# 4. Архитектура проекта простым языком

## Короткая формулировка

Система построена как набор независимых сервисов, потому что разные части проекта имеют разный характер нагрузки: быстрые операции профиля и авторизации, тяжёлая обработка фотографий, работа с маршрутами, кеширование тайлов, AI-запросы и внешние интеграции.

## Основные компоненты

Web PWA / Desktop UI:

- основной интерфейс пользователя;
- React + TypeScript + Leaflet;
- карта, редактор, каталог, профиль, админка;
- может работать как PWA;
- есть desktop-обёртка Tauri.

Android companion app:

- дополнительный мобильный клиент;
- записывает маршрут через GPS;
- хранит локальные черновики;
- синхронизирует маршрут на сервер.

Auth Service:

- регистрация;
- вход;
- JWT access/refresh tokens;
- роли user, moderator, admin;
- профиль пользователя.

Routes Service:

- основной бизнес-сервис;
- маршруты;
- точки маршрута;
- комментарии;
- рейтинги;
- лайки;
- закладки;
- категории;
- AI-чат;
- публичные ссылки;
- статистика маршрута.

Photo Worker:

- фоновая обработка фотографий;
- сжатие;
- генерация миниатюр;
- обновление статуса обработки;
- уведомление клиента о результате.

Tiles Service:

- проксирует картографические тайлы;
- скрывает детали внешних tile-провайдеров.

Cache Service:

- кеширует тайлы;
- снижает количество повторных внешних запросов;
- ускоряет загрузку карты.

## Хранилища

PostgreSQL:

- пользователи;
- роли;
- маршруты;
- точки;
- категории;
- комментарии;
- рейтинги;
- лайки;
- закладки;
- уведомления;
- история AI-чата.

MinIO:

- оригиналы фотографий;
- обработанные изображения;
- миниатюры.

NATS JetStream:

- очередь задач на обработку фотографий;
- события обработки фото.

Redis:

- кеш картографических тайлов.

## Что происходит при загрузке фотографии

1. Пользователь прикрепляет фото к точке маршрута.
2. Frontend отправляет фото в Routes Service.
3. Routes Service сохраняет исходную информацию и публикует задачу в NATS.
4. Photo Worker получает задачу.
5. Photo Worker читает оригинал, сжимает изображение и создаёт миниатюру.
6. Файлы сохраняются в MinIO.
7. Статус фотографии обновляется в PostgreSQL.
8. Клиент получает обновление и показывает миниатюру на маркере.

Почему это сделано асинхронно:

Пользователь не должен ждать тяжёлую обработку изображения в HTTP-запросе. Если вынести обработку в очередь и worker, основной сервис остаётся отзывчивым, а обработчик фото можно масштабировать отдельно.

## Что происходит при публикации маршрута

1. Автор сохраняет маршрут.
2. Включает публичный доступ.
3. Система генерирует уникальный `share_token`.
4. Публичная ссылка открывается без авторизации.
5. Турист видит маршрут, точки, фотографии, описания и статистику.
6. Автор может использовать ссылку, QR-код или iframe-виджет.

## Зачем PostgreSQL

PostgreSQL выбран как основное хранилище, потому что в системе есть структурированные данные, связи между сущностями и геопространственный контекст.

Что даёт PostgreSQL:

- транзакционность;
- связи между таблицами;
- индексы;
- JSONB для гибких данных точек маршрута;
- возможность расширения PostGIS;
- надёжность для пользовательских данных.

## Зачем MinIO

Фотографии не стоит хранить прямо в PostgreSQL: это тяжёлые бинарные файлы, их удобнее держать в объектном хранилище.

MinIO используется как S3-совместимое хранилище:

- оригиналы фото;
- миниатюры;
- обработанные версии.

## Зачем NATS JetStream

NATS нужен для фоновых задач и событий. Главный сценарий — обработка фотографий.

Польза:

- задача не теряется;
- worker может обработать её позже;
- можно запускать несколько worker-ов;
- сбой photo-worker не ломает основной API маршрутов.

## Зачем Redis

Redis используется для кеширования тайлов карты.

Польза:

- меньше повторных запросов к внешним источникам тайлов;
- быстрее загрузка карты;
- меньше зависимость от внешних сервисов.

## Зачем AI

AI в системе не заменяет основную бизнес-логику. Он используется как вспомогательный интерфейс:

- помогает пользователю строить маршрут текстовой командой;
- может вызывать инструменты геокодинга и поиска маршрутов;
- генерирует описания маршрутов по фотографиям;
- снижает ручную работу автора маршрута.

Важно:

Критические функции системы не должны зависеть только от AI. Маршрут можно создать вручную без ассистента.

## Почему web основной, а mobile дополнительный

Автор маршрута часто оформляет маршрут после прохождения: выбирает фотографии, пишет описания, проверяет точки, публикует ссылку. Это удобнее делать на большом экране.

Мобильный клиент нужен в другой ситуации: когда пользователь физически проходит маршрут и хочет записать GPS-трек. Поэтому Android-приложение является companion app, а не полной копией web-клиента.

## Почему микросервисы, а не монолит

Короткий ответ:

Микросервисная архитектура выбрана из-за разного характера нагрузки и необходимости независимого масштабирования отдельных частей: обработка фото, маршруты, авторизация, кеш тайлов и внешние интеграции.

Развёрнутый ответ:

В монолите проще стартовать, но тяжёлые операции обработки фото, внешние API и AI-запросы будут конкурировать с основным API маршрутов. В текущей архитектуре photo-worker можно масштабировать отдельно, кеш тайлов отдельно, auth-сервис изолирован от бизнес-данных, а сбой внешнего AI-провайдера не должен останавливать создание маршрутов.

Честный компромисс:

Для маленького MVP монолит был бы проще. Но для ВКР задача шире: показать проектирование системы с несколькими подсистемами, асинхронной обработкой, публикацией и инфраструктурой развёртывания. Поэтому микросервисы здесь обоснованы не модой, а разделением ответственности и независимой эксплуатацией компонентов.
