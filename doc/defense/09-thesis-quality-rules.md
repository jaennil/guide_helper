# 9. Правила сильного текста ВКР

Цель документа: использовать его как фильтр при переписывании пояснительной записки. Если фрагмент не проходит эти правила, его надо переписать, подтвердить источником или удалить.

## Главное правило

Каждое существенное утверждение должно опираться хотя бы на один тип доказательства:

- источник из списка литературы;
- результат сравнения аналогов;
- требование к системе;
- факт реализации в проекте;
- результат тестирования или измерения;
- пользовательский сценарий;
- явно указанное ограничение или допущение.

Если утверждение нельзя подтвердить, его нельзя писать как факт.

## Структура сильного абзаца

Хороший абзац отвечает на четыре вопроса:

1. Что утверждается?
2. Почему это важно для темы?
3. Чем это подтверждается?
4. Какой вывод из этого следует для проекта?

Слабый абзац обычно содержит общие слова: "современный", "актуальный", "удобный", "эффективный", "инновационный", "масштабируемый", но не показывает критерий и доказательство.

## Правила для введения

- Актуальность должна выводиться из проблемы пользователя, а не из общих слов про цифровизацию.
- Цель должна описывать конечный результат, а не заранее выбранную технологию.
- Задачи должны быть действиями: проанализировать, сформулировать, спроектировать, реализовать, протестировать.
- Объект должен описывать процесс в предметной области.
- Предмет должен описывать методы и средства, которые применяются в работе.
- Практическая значимость должна отвечать на вопрос "кому стало проще и что именно стало проще".
- Архитектурные решения лучше раскрывать в первой и второй главах, а не перегружать ими цель работы.

## Правила для первой главы

- Анализ предметной области должен приводить к требованиям.
- Сравнение аналогов должно иметь критерии, веса и выводы, а не просто описание сервисов.
- Критерии сравнения должны быть связаны с болью целевой аудитории.
- Нельзя писать "аналог не подходит" без объяснения, по какому критерию он не подходит.
- Выбор технологий должен строиться через альтернативы и критерии, а не через "популярно" или "современно".

## Правила для второй главы

- Реализация должна объясняться через требования: какая функция реализует какое требование.
- Описание кода должно быть смысловым, а не пересказом листинга.
- В тексте надо разделять пользовательские функции, серверные компоненты, хранилища и внешние интеграции.
- Для сложных решений нужна причинно-следственная цепочка: проблема -> решение -> почему именно так -> как проверено.
- Названия файлов, команд и программных сущностей можно приводить моноширинным шрифтом только когда это действительно техническая деталь.

## Правила для третьей главы

- Тестирование должно проверять требования, а не просто перечислять тесты.
- Для каждого критического сценария нужен ожидаемый результат и фактический результат.
- Производительность должна сравниваться с заранее указанным порогом.
- Экономическая часть должна опираться на явные допущения: трудоёмкость, ставка, число пользователей, экономия времени.
- Заключение должно показать, что все задачи из введения решены.

## Запрещённые паттерны

- "Система является современной" без критериев современности.
- "Повышает эффективность" без метрики эффективности.
- "Уникальная система" без ограниченной формулировки и критериев сравнения.
- "Микросервисы обеспечивают надёжность" без объяснения, какой сбой изолируется.
- "AI улучшает пользовательский опыт" без конкретного сценария.
- Англицизмы при наличии русского аналога: "шеринг" -> "публикация" или "обмен", "бэкенд" -> "серверная часть", "фронтенд" -> "клиентская часть".
- Скобки с пояснениями, которые можно встроить в предложение.

## Рабочий алгоритм переписывания

1. Прочитать абзац и выделить главное утверждение.
2. Найти доказательство: источник, таблицу, требование, тест или факт реализации.
3. Убрать оценочные слова без критерия.
4. Связать абзац с задачей ВКР или пользовательской проблемой.
5. Проверить, что следующий абзац логически вытекает из предыдущего.

## Быстрый чек-лист перед сборкой PDF

- Во введении нет преждевременного выбора технологий в цели.
- Все задачи из введения закрываются разделами и заключением.
- В первой главе требования выведены из проблемы и анализа аналогов.
- Во второй главе реализация сопоставлена с требованиями.
- В третьей главе тесты сопоставлены с требованиями.
- Все цифры можно объяснить устно.
- Все спорные утверждения имеют ссылку, таблицу, тест или ограничение.
- Англицизмы заменены русскими аналогами, если это возможно.
